# 测试与验证

本章讲这个生态怎样确立正确性：有哪些场景、它们可以碰什么、怎样运行、什么算证据。这些是项目的规则而不是包的接口——它们不增加定义条目——但正因如此，本书其余部分描述的公共行为才可信，而它们同样适用于建立在各包之上的应用或扩展。

## 只测公共接口

<!-- index: 公共测试; 验收清单 -->

受维护的测试通过包入口声明的接口行使可观察的输入、输出、错误、回滚与生命周期。它不测私有辅助、内部数据结构、源码文本、调用次数或已退役的行为；夹具与辅助函数遵守同样的规则，间接、反射或故障注入都不构成私有访问。当某个场景看起来需要私有符号时，正确的回应是把事实移到公共接口之后、或者改为测试可观察行为——绝不为了让测试留着而把符号升为公共 API。

每个包在 `tests/acceptance.json` 里清点它维护的 Lisp 正确性场景，一条场景一个条目，附可观察的目的。清单是包声称验证了什么这一点的契约：`make test` 恰好跑这套公共套件，`make check` 再一起跑结构门禁、字节编译、全新入口绑定与源码签名校验。这里没有单独的内部套件，因为内部测试断言的是实现，而不是消费者看见的行为。

## 无头断言

<!-- index: ERT; 串行运行; 有界失败输出 -->

场景是 ERT 测试。工作区运行器 `scripts/run-acceptance.py` 用一个 checkout 上的咨询锁把运行串行化：并发的运行以退出码 75 被拒绝，或者最多等待 `--wait SECONDS` 秒。这正让重复的本地运行与后台作业可以安全地共用同一份构建产物。

失败的 ERT 测试往往会打印条件，而框架的条件可能很大或带环。运行器把 pretty-printer 换成受 `--print-length`（默认 6）、`--print-level`（默认 3）与硬上限 `--max-condition-bytes`（默认 8192）约束的普通打印，所以失败报告保持可读。两个习惯让单条断言不惹麻烦。把返回大活对象的调用结果——Runtime、缓冲区、树——绑定到局部变量，再对局部变量断言，因为 ERT 会捕获求值后的参数，`should` 形式里的大对象会让每次失败报告都巨大。打印框架内容时用 `buffer-substring-no-properties` 取文本，并绑定 `print-circle` 与打印上限；活的 Runtime 或回溯可能带循环闭包与文本属性，`%S` 会永远展开。写给 Emacs 加载的 Lisp 文件，包括临时探针，首行都要有 `;;; -*- lexical-binding: t; -*-`。

## 真实 GUI 里的验证

<!-- index: GUI 验证; 视口档位 -->

无头断言证明行为，不证明外观与延迟。可见或交互相关的改动要在真实图形 Emacs 会话里验证：按用户打开的方式打开受影响的示例或应用，检查宽、常规、紧凑、矮四种视口档位，并在交互中途做一次缩扩，因为一张截图里看着正确的布局，换一个宽或高就可能坏掉。批量运行既不能证明渲染、也不能证明输入延迟：重绘与输入调度只在 GUI 里参与。工作区手册保存着在完整用户 init 中验证隔离检出的配方，包括怎样启动或复用 server、核对帧与已加载的代码。

自动化工具的性能场景是这套验证的一部分，而不是它的替代品。`scripts/performance.py` 在 batch 模式下跑注册场景来测 operation 与 CPU 成本，或在 GUI 模式下测真实渲染与输入计时；`gate` 是 GUI server 内快速的逐改动检查，`run`、`compare` 与 `summarize` 用于诊断与取证。在把一项功能宣布完成之前，场景的数据流、可见渲染与交互仍要由人看过。

## 性能门禁

<!-- index: 性能门禁; 基线; 安静树 -->

性能与正确性同样严肃地验证。改动之前用 `make verify-baseline` 建立基线，再用 `make verify BASELINE=…` 对比可重复的运行；报告同时带正确性结果、延迟采样与回归比较，最终的结论用三组独立采样。开发期间只筛改动影响的代表性场景，完整矩阵留给验收。在安静的树上测量：测量期间任何源码变化都会把整次运行标为未验证，所以验证在改动提交之后运行。失败、缺失或不可比的性能门禁保持未验证——包括本来就存在的失败——因为一个缺席或过期的数字不是通过。[性能工程](performance-engineering.md)一章完整描述记录器与测量规则。

## 诊断即缺陷

<!-- index: 诊断; 抑制 -->

框架在测试或示例运行期间报告警告时——组件校验、渲染器警告、字节编译或加载错误——那份报告就是发现，不是噪声。它要被读、被追到拥有它的层、在那里修。它绝不用 `ignore-errors`、更宽的 `condition-case`、抑制警告或排除测试来消音。只有当诊断本身是错的，抑制才正当，而那时修复属于抛出诊断的地方。同理，不为了把失败变绿而削弱检查、添加排除或跳过测试；当某项检查过期时，把它更新到当前契约，同时保留它的行为覆盖。

## 手册也在门禁里

<!-- index: book 门禁; 翻译校验 -->

手册自己的门禁把文档放在同一标准上。`make -C etaf-manual book-check` 校验章节结构、定义条目签名与 provider Commentary 逐字一致、文档化包与词表的覆盖、链接、正文的公共符号规则、段行纪律与两种语言的对齐；活示例验收会挂载两种语言的每个 `:run` 示例，所以求值或挂载失败的示例会让门禁失败。公共接口变化时，受影响的章节在同一次交付里更新两种语言，这正是手册始终描述当前代码、而不是更早版本快照的原因。

## 证据的处理

<!-- index: 证据; 未验证 -->

测量产生原始证据，原始证据留在版本控制之外；在打开具体失败日志之前先看紧凑结果。测量期间检出发生变化的运行，无论数字如何都标为未验证；比较数据缺失或过期的运行不算通过；有所改善的结论在重复一遍之前不被采信。同样的纪律适用于正确性：没有跑过的场景，或对着错误代码跑的场景，什么都没有证明。
